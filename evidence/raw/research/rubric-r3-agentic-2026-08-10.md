# Senior Agentic AI Engineer: Advanced Topics Rubrics (2026)

## LangGraph in production (StateGraph, checkpointing, HITL, streaming, durable execution, resume)
- **Comfortable bar (checkable):** Can implement a LangGraph `StateGraph` and use checkpointers to persist state. Understands how to configure durable execution (using PostgresSaver or memory saver) and use streaming modes for real-time outputs. Knows how to pause execution with interrupts and resume graphs (with `Command(resume)`) for human-in-loop interventions.  
- **Strong bar:** Designs pipelines with fault tolerance and state recovery. Uses both checkpointers (short-term state) and stores (long-term) so agents can resume after crashes. Leverages LangGraph streaming and breakpoints for observability and HITL control. Optimizes state schemas and retention policies to avoid checkpoint bloat. Implements durable GraphRunners or LangSmith Agent Server to auto-handle persistence and resume.  
- **Probe questions:** “How do you persist an agent’s state across runs in LangGraph? Explain checkpointers vs stores.”; “Describe how you would add human-in-the-loop checks in a LangGraph workflow.”; “When and how do you use streaming in LangGraph pipelines? What are streaming modes?”; “How do you recover or resume an interrupted graph execution after a crash?”; “What happens if a graph’s subgraph exceeds retention limits in the PostgresSaver?”  
- **Failure stories / anti-patterns:** Forgetting to persist state, causing conversation loss on crash. Using static interrupts for production HITL, which blocks pipelines (should use dynamic interrupts instead). Overloading one graph without checkpoints, causing out-of-memory or lost context. Not batching streaming outputs, yielding high latency. Ignoring exceptions inside graph nodes leading to silent failures.  
- **Anti-goals:** Building stateless chains when long-running state is needed. Trying to manage state manually outside LangGraph (e.g. external DB without checkpointers). Using LangGraph for trivial one-step tasks.  

## LangChain fluency & limits (LCEL/chains/retrievers/callbacks – when to use vs avoid)
- **Comfortable bar:** Able to build basic LangChain chains and use retrievers for RAG. Knows LLMChain, SequentialChain, and use of `callbacks` for logging or streaming. Uses LangChain Expression Language (LCEL) to declaratively compose pipelines with built-in streaming/batch support. Understands when to use vector retriever vs relying on prompt alone (retrievers for QA with external docs).  
- **Strong bar:** Crafts efficient chains (≤5 steps) and uses LCEL for complex flows. Integrates automatic callbacks and LangSmith tracing via LCEL. Knows advanced features: agentic chains for decision-making, progressive disclosure (Skills pattern), and uses `StreamingStdOutCallbackHandler` to reduce latency. Evaluates trade-offs: when an agent is overkill (“use chain if steps known”), or when memory/prompt length limits mandate a chain. Applies custom callbacks for monitoring and uses LangChain’s `Router` and `Handoff` patterns.  
- **Probe questions:** “What is LCEL and how does it differ from traditional chains?”; “Describe when to use a chain of tools vs a single prompt.”; “When is a retriever (RAG) necessary, and when might it hurt performance?”; “How do callbacks work in LangChain, and why might you use them?”; “What are common pitfalls of LangChain agents (e.g. ReAct agents) and how do you mitigate them?”  
- **Failure stories / anti-patterns:** Over-chaining (too many steps) causing brittle systems. Misusing agents for simple flows – e.g. letting an agent loop unnecessarily rather than a chain (leads to unpredictable loops). Ignoring caching of chain outputs, blowing up token use. Blindly trusting chain output without validation. Failing to catch tool misuse or bad outputs because no callbacks or QA checks.  
- **Anti-goals:** Using LangChain where a simple direct API call suffices. Forcing a chain for trivial tasks. Assuming LangChain components eliminate all prompt engineering – chains still need well-designed prompts.  

## Multi-agent orchestration (supervisor/router/hierarchical teams)
- **Comfortable bar:** Understands multi-agent patterns: e.g. a supervisor agent calling specialists (“subagents”) vs parallel router pattern. Knows roles like manager vs workers in an agent “crew”. Can sketch a basic orchestration: e.g. one agent delegating tool-specific tasks, or an agent loading skills on demand.  
- **Strong bar:** Designs a multi-agent system with clear delegation. Implements a supervisor or router that dispatches to stateless specialist agents and gathers results (centralized “subagents” pattern). Or configures router classifiers to run experts in parallel and synthesize answers. Sets up a hierarchical flow (manager → sub-crews → workers) with retry logic (as in CrewAI flows). Balances autonomy vs determinism: uses task queues, hierarchical Flows with guardrails (e.g. only one manager delegates, specialist teams have narrow roles). Chooses architecture by context: e.g. centralized subagent control when domains are distinct, router pattern when many domains can run in parallel.  
- **Probe questions:** “Compare the subagents (supervisor) vs router vs handoff patterns in LangChain. When would you use each?”; “How do you design a hierarchical multi-agent workflow (e.g. manager vs worker agents) for complex tasks?”; “What strategies ensure specialist agents don’t duplicate work?”; “How do you handle task failures or loops in a multi-agent team?”; “Describe a scenario where parallel dispatch (router) is better than a sequential handoff.”  
- **Failure stories / anti-patterns:** Overspecialization: building a team when a single agent suffices, adding needless complexity. Lack of coordination: multiple agents working on same subproblem (duplication). Single point of failure in supervisor: if manager crashes, whole workflow halts. No state transfer: forgetting to pass context between agents, losing information. Excessive chats: uncontrolled handoffs causing infinite loops. Ignoring latency of parallel calls (spawn too many agents).  
- **Anti-goals:** Avoid flat, monolithic design (“all-in-one agent”) when team is needed. Avoid “ready-made orchestration” without clear data flow. Don’t hard-code one agent’s role all the way; prefer clear interfaces.  

## Agent evaluation & tracing (LangSmith/Langfuse/Phoenix/OpenTelemetry-style)
- **Comfortable bar:** Uses an observability tool (like LangSmith, Langfuse, or Phoenix) to capture agent traces. Understands that a “trace” is the full step-by-step execution (each LLM call, tool call, retrieval, branch). Can retrieve token counts and latencies for each step. Knows how to enable tracing via OpenTelemetry: e.g. emit `gen_ai.*` spans for LLM calls so Langfuse records token usage and cost.  
- **Strong bar:** Implements full pipeline metrics: uses LangSmith or Langfuse to record and analyze agent execution trees. Tracks cost: aggregates token usage and compute cost per trace. Adds custom metrics (loop counts, #tool calls). Sets up offline vs online evaluation: offline experiments with saved traces, and online evals on live traffic. Connects LLM-as-judge evaluators to score semantic correctness. Utilizes insights: e.g. LangSmith Insights to cluster failure modes. Deploys OpenTelemetry instrumentation so any language stack can send traces.  
- **Probe questions:** “What is an agent trace and what information does it contain?”; “How would you instrument an agent pipeline to measure its cost and iteration count?”; “Compare LangSmith, Langfuse, and Arize Phoenix for agent tracing and evaluation.”; “What are key metrics for agent evaluation (trajectory length, tool accuracy, etc)?”; “How do you set up continuous evaluation (CI) with LLM-as-judge?”  
- **Failure stories / anti-patterns:** Only evaluating final answer; missing intermediate failures. No tracking of token cost, leading to runaway spend. Ignoring tracing leads to blind spots: e.g. an agent repeating retries endlessly. Overlooking loops: e.g. agent stuck calling the same tool in a loop (should be caught by trajectory metrics). Relying solely on sample logs instead of structured traces; inadequate observability.  
- **Anti-goals:** Not considering full session context (threads) when evaluating. Using only batch LLM evals; neglecting open telemetry or built-in tooling. Skipping instrumentation until after major deployment.  

## Agent benchmarks & eval CI (SWE-bench, GAIA, Tau-bench; LLM-judge and red-team CI gates)
- **Comfortable bar:** Knows major benchmarks: SWE-bench for software engineering (bug-fix code generation), GAIA for multi-step reasoning with tools, Tau-bench for policy-compliant customer service tasks. Can run a model on these benchmarks (understand pass rates measure correctness). Sets up basic unit tests or dataset for agent flows.  
- **Strong bar:** Understands limitations: e.g. that SWE-bench scores depend on scaffolding, or GAIA suits open-domain tasks, Tau-bench covers compliance constraints. Builds CI pipelines: uses LLM-as-judge scripts and metric libraries (e.g. DeepEval) to automatically check tool calls and final outputs. Creates golden test sets for regression testing: runs reference-based evaluations in CI on model/prompts changes. Integrates red-team and safety evals: e.g. scripted jailbreak or injection cases as CI tests, following OWASP agentic categories. Automates nightly or pre-release evals of agent performance (tool accuracy, path efficiency, policy compliance), with alerts on regressions.  
- **Probe questions:** “What do SWE-bench, GAIA, and Tau-bench measure? When would you choose each?”; “How do you incorporate agent benchmarks into CI? Give an example pipeline.”; “Explain LLM-as-judge: reference-based vs reference-free evaluation.”; “How do you build a private eval set for your production tasks?”; “Describe how you would red-team an agent (prompt injection, malicious tool responses).”  
- **Failure stories / anti-patterns:** Blindly trusting a single benchmark score; misinterpreting it as production performance. Skipping a private evaluation: leading to surprises in real tasks. No guardrails in CI: e.g. failing to catch policy-violating outputs. Using an LLM judge without golden answers in CI (leads to false negatives/positives). Poor test dataset: not covering edge cases, causing regressions to slip.  
- **Anti-goals:** Relying on public leaderboard positions for deployment decisions. Writing only generic tests (e.g. grammar checks) and ignoring agent-specific failures (tool misuse). Thinking a single AI eval tool is enough: need layered tests and human review.  

## Test-time compute & reasoning models in agent pipelines (o-series/DeepSeek-R1 style; queues + SSE; routing cheap vs reasoning models; cost)
- **Comfortable bar:** Understands multi-tier model strategies: e.g. first use a smaller model or a classifier to identify tasks, then a larger model for heavy reasoning (hybrid routing). Knows about asynchronous pipelines: e.g. using task queues (Celery, RabbitMQ) and streaming (Server-Sent Events) for long-running agent tasks. Aware of token/call cost trade-offs: e.g. that expensive models (GPT-4o, RLMs) should be used judiciously.  
- **Strong bar:** Implements specialized “reasoning” models or extended-compute pipelines (like OpenAI o1 or DeepSeek-R1) where the model performs multi-step inference. Designs scheduling: e.g. using an inference queue for heavy queries with progress via SSE, so users see partial updates. Employs speculative sampling or blackboard patterns to speed reasoning under cost constraints. Routes inputs: simple queries answered by cheap LLM (GPT-3.5-like), complex queries escalated to expensive RLM (GPT-4o/R1). Monitors performance vs cost: tracks latency and cost per query, and implements caching or early-exit (if cheap model already answers).  
- **Probe questions:** “What is ‘test-time compute’ and how does it relate to agent reasoning?”; “Explain how DeepSeek-R1 or GPT-O1 use extended inference for better reasoning.”; “Describe a multi-tier model setup (planning vs execution models) in an agent. Why use it?”; “How would you handle long-running reasoning tasks in a web service?”; “What techniques reduce LLM token/call costs in agents?”  
- **Failure stories / anti-patterns:** Using the same large model for every step (skyrockets cost). Ignoring cheaper models: e.g. always calling a top-tier model even for simple tasks. Synchronous design: blocking the user with no feedback for expensive ops. No batching or caching, leading to repeated calls. Poor queue management: tasks stuck, no back-pressure. Not measuring cost: runaway bills from loops or excessive iterations.  
- **Anti-goals:** Forcing trivial queries through “slow thinking” pipelines unnecessarily. Over-optimizing cheap model logic at expense of correctness. Sacrificing user experience with excessive delays (unless necessary).  

## Agentic guardrails (Guardrails AI vs NeMo; layered defense; OWASP LLM risks)
- **Comfortable bar:** Knows the key threat categories from OWASP GenAI: prompt injection, data leakage, unauthorized tool use (excessive agency). Can identify simple mitigations: e.g. input validators, output sanitizers, and using OpenAI/other moderation APIs. Aware of guardrail libraries: e.g. Guardrails AI (composable validators for content, format, PII), NVIDIA NeMo Guardrails (dialogue and execution rails), and their purposes.  
- **Strong bar:** Architect a layered safety stack: input filters, schema validation on function calls, a retrieval “rail” to scan external content for injections, output filters for disallowed content, and tool-call gating for excessive or undesired actions. Chooses guardrail frameworks appropriately: e.g. uses Guardrails AI for flexible validators (PII, bias, etc), NeMo for conversation-level rails and execution gating. Implements real-time safety: uses fast classifiers on-turn (like Llama Guard or Morph Reflex) inline to catch threats under latency budgets. Incorporates both build-time (red-team tests, static analysis) and runtime (live monitoring) guardrails. Sets up adversarial tests based on OWASP: e.g. injection attempts, hallucinated tools, data exfiltration scenarios.  
- **Probe questions:** “What are OWASP LLM01 and LLM06, and how do you defend against them in agents?”; “Compare Guardrails AI and NVIDIA NeMo in terms of use cases.”; “Describe a multi-layer guardrail strategy for an agent pipeline.”; “How do you detect and handle a hallucinated tool call at runtime?”; “What role do training-time safety and runtime guardrails each play?”  
- **Failure stories / anti-patterns:** Assuming the LLM’s training is enough – failing to add runtime checks (e.g. an agent running prohibited tool calls). No input sanitization: falling for prompt injections via conversation or RAG. Over-relying on a single classifier (which may have high false positives) without contextual checks. Skipping tool-call gating: agent escalates beyond authority. Not segmenting shield layers – e.g. only output filter (too late for an injection that already occurred). Using an LLM judge for safety inline (adds too much latency) instead of a fast classifier.  
- **Anti-goals:** Sole reliance on static content filters (no semantic understanding). Trying to hardcode all policies in prompt (ineffective against indirect attacks). Ignoring least-privilege in tools (give agent only needed permissions).  

## Overlap cleanup

- **MCP-architecture vs Multi-Agent:** LangGraph statefulness, checkpointing, streaming, and HITL relate to production reliability (more MCP/backend architecture). Multi-agent orchestration and related failure modes belong to **multi-agent**. (Overlap: both deal with workflow design, but LangGraph is about execution model vs multi-agent is about team coordination.)  
- **Guardrails vs Production-Security:** Agentic guardrails (Layered defense, OWASP risks) squarely in **production security**, overlapping with multi-agent (since excessive agency is an agentic threat). Agent evaluation (cost tracking) also touches security (privacy via telemetry), but mainly observability.  
- **Benchmarks & CI:** Overlaps with evaluation (e.g. evaluation tools trace agent runs, agent testing references guardrails). CI gating includes red-teaming (security). These belong to **production quality/evaluation**.  
- **LangChain fluency & limits:** Some overlap with multi-agent (chains vs agents) and MCP (LangChain vs LangGraph choice), but mostly in **framework usage**; ensure not duplicating with workflow vs agent chapter.
